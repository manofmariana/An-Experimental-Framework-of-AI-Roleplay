# Ofair — Open Framework of AI Roleplay

面向 AI 角色扮演的开放框架。骨架是三套自研机制——**异步时序调度系统**、**TAG 过滤与声明式占位符组装**、**自定义变量与数值规则（WIP）**——真相存于结构化事件日志与变量库，而非聊天文本。

> **注意：本项目的全部代码由 AI 编程（AI coding）完成。**
>
> 状态：**pre-alpha，活跃开发中**。核心运行时（调度/真相层/注入管线/WebUI）已可用并能完整游玩；P2 阶段（TAG / 变量 / 占位符系统）已落地 4/7。欢迎对架构与实现感兴趣的朋友交流。

## 设计动机

主流的 AI 角色扮演软件（以 SillyTavern 为代表）普遍采用**单上下文结构**：每轮把角色卡、世界书与全部历史拼成一个大字符串，由一个模型同时扮演所有角色。这个结构简单直接、生态成熟，但也带来几个绕不开的结构性权衡：

1. **模型天然全知**——所有信息进入同一个上下文，秘密、谎言、戏剧反讽只能靠提示词约束维持；
2. **聊天文本即状态**——修改历史靠手动编辑文本，没有结构化的一致性保障；
3. **扩展多以前端补丁形式存在**——前后端耦合较紧，新能力的开发成本偏高。

Ofair 在这些权衡上选择了另一条路，对应四条设计哲学：**真相层与视图分离**（事件日志 + 变量库 + 知识账本是唯一真相，正文与角色感知都只是渲染视图，视图不许反向污染真相）；**时序与感知是程序问题，不是提示词问题**（调度、过滤、落账全部确定性实现）；**需要判断的才调用 LLM，纯工序做成确定性服务**（LLM 调用只花在创作与裁决上）；**通用优先于特供**（核心保持后端无关，模型特定的优化下沉到边缘层）。

## 三大核心机制

### 异步时序调度系统

连续时间轴离散事件调度（DES），零 LLM。每个角色携带**到期时刻** `timer`（绝对分钟标量），调度 = 扫描全体角色取最近到期者弹出、时钟跳转；**同步组、行动顺序、先攻、行动周期全部从角色变量派生**——组不是实体、不持有任何变量，因此回溯零特例。无判定轮是默认形态：无人请求裁决时角色照常互相对话，GM 裁决是例外（标记触发 / 周期硬保险），LLM 调用频率从"每圈一次"降为按需。邀请/频道（远程同场）、突发事件（唤醒长期休眠组）等机制均建在时钟之上。

### TAG 过滤与声明式占位符组装

TAG 是内容可见性的判定通货：内容侧挂 `{name, level}`（1-7 级），对象侧持纯名集合，判定式 = 同级取或、跨级取与。事件/世界书/角色/世界**四大内容根同构**为末端外壳树，统一过同一求值器逐末端过滤——**认知隔离由结构保证，不靠"请假装不知道"**。提示词注入全走声明式占位符目录（程序组装源 + 落盘四根路径，编辑期机检），模板档内化、运行期在线可编辑、下一轮激活即生效。

### 自定义变量与数值规则（WIP）

全部状态存为**模板声明的变量树**：容器/结构化数组/末端三类节点，末端 = `{value, tags, formula?}` 外壳，可挂 TAG、可声明从动公式（写后按依赖图拓扑整根重算）。变量变更是确定性代码：GM 输出的 deltas 直接落库，可审计、可回滚，回溯时随 changes 逐字节还原。**数值规则/自定义动作**（公式表达式 + 骰子 + 效果机械落账）设计已定案、实现进行中。

## 架构速览

```
              玩家输入（主控意图）
                      │
                      ▼
        ┌──────────────────────────────┐
        │ 异步时序调度（连续时间轴 DES）  │  零 LLM：到期弹出、
        │ 组/先攻/行动周期全派生         │  组划分、计时器
        └──────────────┬───────────────┘
                       ▼
        ┌──────────────────────────────┐ ◄── 确定性落账（deltas / VarChange，
        │ 真相层：事件日志 + 变量库       │      步边界原子提交，append-only）
        │ + TAG 注册表/变量模板          │
        └──────────────┬───────────────┘
                       ▼ 全量供给
        ┌──────────────────────────────┐
        │ TAG 过滤（四根内容逐末端求值）  │  零 LLM：读者可见集
        └──────────────┬───────────────┘
                       ▼
        ┌──────────────────────────────┐
        │ 声明式占位符组装（模板×目录）   │  零 LLM：提示词渲染
        └──────────────┬───────────────┘
                       ▼ 提示词
        角色 Activation ×N ──决策包──► GM Activation ──裁决包──► 正文 Activation
        （私域上下文，唤醒制）            （唯一全知者）            （纯渲染器）
                       │
                       ▼
              瘦前端（WebUI 纯渲染器）
```

**关于 Agent 的定位**：本框架不使用自主 Agent 框架。所有 LLM 调用都是**无状态 activation**——无工具调用、无对话历史、无跨调用缓存，每次激活从真相层现取现组装。多角色"人格"是调度 + 过滤 + 组装三套机制叠加出的效果，不是 Agent 编排。未来可能基于这些机制**推出 Agent 版本**（工具调用、世界书治理、新角色热生成等，见 ROADMAP P3），但那是在机制之上的产品层，不是框架本体。

## 技术栈

- **后端**：TypeScript ESM（Node.js，无构建步骤，`tsx` 直接跑 TS）；依赖只有 `openai` / `ws` / `zod`；
- **前端**：无构建 Vanilla 单页应用；
- **测试**：Node 内置 `node:test`，四层套件（unit / contract / application / integration）+ 依赖方向机械审计；
- **包管理**：npm，本地运行的私有应用，无打包/发布流程。

## 快速开始

```bash
npm install
npm run serve        # WebUI 服务，默认 http://127.0.0.1:8787
```

或直接运行 `Ofair-WebUI.bat`（起服务 + 自动开浏览器）。首次使用在 WebUI「配置」页填入 LLM API 密钥与模型预设（或设 `OFAIR_API_KEY` 等环境变量），然后新建会话选择示例世界包 `baitan` 即可游玩。

常用开发命令：

```bash
npm run check        # 日常门禁 = typecheck + 依赖审计 + 纯单测套件
npm test             # 全量测试
npm run test:unit / test:contract / test:application / test:integration
```

注意：改代码后必须重启服务再**新建**会话验证——存档带版本闸，版本不符会拒绝加载（防"旧代码 + 新模板"混合态，是设计不是故障）。

## 项目结构与文档

- `src/` — 后端源码（`types.ts` 契约 / `scheduler/` 调度派生 / `compile/` 模板渲染 / `truth/` 真相层 / `agents/` 无状态 activation / `application/` 会话内核 / `server/` HTTP+WS）；

## 开发者留言

这个项目的根本初衷是**认知隔离**——TAG 系统与占位符组装是整个框架的主心骨，都是为它服务的。而认知隔离要成立，逻辑上就必须做到多角色：每个角色独立行动、独立感知、独立决策。这是 Ofair 与传统 AI 角色扮演软件较大的区别——酒馆类软件其实都有群聊系统，但就目前的实际体验而言，它们的群聊可用性还不如一对一单聊。

多角色一旦成立，调度就成了绕不开的问题。常见的调度方案——固定顺序、随机、各种概率或条件触发——都无法完美实现角色扮演需要的效果，所以我设计了这套复杂的异步时序调度系统。多角色还带来一份额外收益：它为联机游玩和切换扮演对象提供了很高的适配性。

但坦白说，我对当前的调度系统并不满意。它很复杂，机制上甚至可能有些臃肿、有过度设计之嫌——我的评价是**可用，但不完美，谈不上理想状态**。仅从质量角度出发，最好的调度应该交给一个单独的 AI 来负责；但这会引出一连串问题：这个调度 AI 的触发频率如何定？每个角色行动都激活一次显然不现实，比较现实的选择或许是每次安排好一个批次、批次结束后再激活。那它的存在形式又该是什么——无状态调用，还是 Agent？这些问题目前都没有答案。

因此从实现角度出发，项目会继续沿用现在的调度系统，直到项目整体趋于完善、其他系统被证明稳定有效之后，才可能考虑更换调度。

而比起换调度，**开发一个 Agent 版本的优先级更高**。这个版本会复用 TAG 系统、部分利用当前调度，但不再依赖现有的占位符等提示词组装环节。我预期能从 Agent 化中获得最大质量提升的是 GM 身份——因为到那时，可以把更多、更复杂的任务交给它了。
