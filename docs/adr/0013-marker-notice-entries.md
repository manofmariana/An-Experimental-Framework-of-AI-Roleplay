# 标记通知化：通知条目入工作集 + 同 type 固定 ID 复用

**决定**：

- **标记从「不进任何注入」翻案为「通知条目注入」**：gm_request/leave/recall/contact 四标记在消费点（planActorDecision）由程序生成**系统通知条目**入工作集——`{id, author:"system", notice:{type, actor, means?, targets[]}, tags}`，载荷纯结构化参数、无文本（文案 = 投影层机械组装 + 占位符模板渲染）。confirm 不生成（它是应答本身）。标记机制本身（触发 GM/邀请投影）原样保留，通知条目是并行的注入镜像、不替代 markers。
- **通知条目同 type 复用固定 ID**（`notice:{type}`）：同类型实例后来者居上（先摘后附），工作集内同 type 至多一条。通知是临时内容、昙花一现——生命周期随工作集清算（GM 清算即消亡），GM 恒见（权重 6 恒过，无需特例）。新类型（如动作通知）按正常规则分配 ID。
- **tags 生成时按焊死映射安插且为纯函数**：contact = 感知 `{aud@1, vis@1}` + 目标 cid@2 + 手段 `{A@3, V@3}`（同级取或，工具双向对称），其余 = `{vis@1}`。载荷镜像标记本身（目标归一化、不做有效性校验——校验归标记执行层），因此投影重建（回滚/GM 编辑切片）经同一纯函数再生，与落账逐字节一致。
- **言行条目的条目级 TAG 挂载不落条目**，渲染时按焊死映射从当前真相派生（发言 `{aud@1, vis@1}` / 行为 `{vis@1}`；字段 A 追加频道@2 + `{A@3, V@3}`、字段 B 追加地点@2；等级方案 感知（1) → 归属（2) → 手段（3)）——保住 `{cid, decision}` 引用与投影重建的逐字节还原机制（历史 channel/location 不可从步骤序列重建）。

**为什么**：

- 标记的程序作用（离场/召回/联系）此前对其他角色完全不可见，只有 departure_notices 一个专门占位符补丁；通知条目把「发生了什么调度事实」统一搬进工作集这个既有的未裁决素材通道，注入/过滤/清算/回放全部复用工作集机制，不再为每种通知开专线。
- 固定 ID 复用而非逐实例分配：通知是昙花一现的临时内容，同类型多条只有最新一条有感知价值（两次离场通知只需知道最新一次）；固定 ID 让复用语义显式化（先摘后附 = 后来者居上），且投影重建无需任何分配器状态。
- 载荷镜像标记而非镜像校验结果：投影重建只有步骤序列（decision.markers），没有消费时刻的角色状态；纯函数镜像保证落账与重建同源同结果。未知目标等非法输入由标记执行层 warn 忽略，通知层不重复判定。
- 言行条目挂载渲染时派生而非落条目：挂载依赖 channel/location 这两个易变变量（联系标记与发言同轮决策时，落账点频道尚未分配），渲染时取当前真相既正确又让回滚/编辑重放零适配。

**代价**：

- GM 恒见工作集 ⇒ GM 会看到通知条目（含 contact 通知）——定案语义，GM 提示词对通知条目的教学措辞归内容工作。
- 同 type 复用意味着较早的同类型通知被覆盖即消失（如两人先后离场，工作集只留后一条 leave 通知）；言行条目本体仍在，事件转写不丢事实，损失限于注入层的通知文案。
- 言行条目挂载渲染时派生 ⇒ 决策后 channel/location 变化（如当场离场清频道）会改变该条目的可见域——工作集生命周期短（一轮一清），漂移窗口可接受。
- 通知载荷 targets 不做有效性校验（未知目标也会出现在通知里）——非法输入本就是提示词契约违例，执行层已 warn。
